### 1. Full Architecture of Apache Kafka : with your comments/explanation

Apache Kafka is a system that allows applications to exchange data in real time.

For example, when someone buys a product on Amazon, the online shop sends an event to Kafka.

The application sending the event is called a **producer**. Kafka organises the events into categories called **topics**, and each topic can be divided into **partitions** to distribute the workload (and keep events in order within each partition).

Kafka runs on servers called **brokers**. Several brokers working together form a **cluster**, where **KRaft controllers** manage the cluster metadata and partition leadership. Brokers can also replicate data so that the system keeps working if a server fails.

Other applications, called **consumers**, read the events. For example, the warehouse can prepare the package, an email service can notify the customer, and analytics can record the sale. Consumers are organised into **consumer groups**: different groups (like different departments — warehouse, email, analytics) each get all the events independently, while multiple consumers inside the same group (like coworkers in the warehouse) split the partitions so they work faster without duplicating work.

Consumers use **offsets** to track their progress (an offset is a number that identifies the position of an event inside a partition), and Kafka keeps the events for a configured period, which allows them to be read again.

In short, Kafka acts as a central system that connects applications and allows them to share information reliably and quickly. It is a push and pull tecnique.

### 2. Class Notes: Handling Consumer Lag & Out-of-Order Events Across Partitions

#### What Is Consumer Lag?
- **Consumer Lag** is how far behind a consumer is compared to the latest message in its partition (`Lag = Latest Offset − Consumer Offset`).
- In a consumer group, different consumers (`X`, `Y`, `Z`) read different partitions independently and at different speeds, so one consumer can lag behind another.

#### Class Example (Why Lag Can Cause Wrong Data)
Suppose the same user updates their email twice:
- **Event `101` (2:00 PM):** `blessing123@gmail.com` → Producer `P` sends it to **Partition 0** (read by **Consumer `X`**)
- **Event `104` (2:04 PM):** `blessing789@gmail.com` → Producer `P` sends it to **Partition 1** (read by **Consumer `Y`**)

If **Consumer `X` is lagging** (slower) while **Consumer `Y` is fast**:
1. **Consumer `Y`** reads Event `104` (`blessing789@gmail.com`, 2:04 PM) **first** and writes it to the database (via **Kafka Connect / KC**).
2. Later, **Consumer `X`** catches up and reads the older Event `101` (`blessing123@gmail.com`, 2:00 PM) **second**, writing it to the database.
3. **Problem:** The older 2:00 PM email overwrites the newer 2:04 PM email! This happens because Kafka **only guarantees order within a single partition**, not across different partitions.

#### How to Handle & Prevent This
1. **Use a Message Key (Same Entity → Same Partition):**
   - Attach a key like `user_id` when producing the event. Kafka sends all messages with the **same key to the same partition** (so both `101` and `104` go to Partition 0). Because only one consumer (`X`) reads Partition 0 in offset order, `101` (2:00 PM) is always processed before `104` (2:04 PM) — even if Consumer `X` lags.
2. **Timestamp / Version Check at the Database (Sink):**
   - Store the event timestamp with the record and only update if `incoming_timestamp > existing_timestamp`, so a late 2:00 PM event can never overwrite a newer 2:04 PM event.
3. **Monitor & Reduce Consumer Lag:**
   - Track consumer lag per partition, optimize slow consumers, and scale consumers (up to the number of partitions) to keep lag low.

### 3. Class Notes: Producer Acknowledgements (`acks`: `0`, `1`, and `all`)

When a producer sends a message to Kafka, the `acks` setting controls **how many broker confirmations** the producer waits for before considering the write successful (speed vs. safety trade-off):

| Setting | Meaning | Trade-off |
| :--- | :--- | :--- |
| **`acks=0`** | **No wait** — producer sends the message and does not wait for any confirmation from Kafka. | Fastest, but **message loss can go unnoticed** (e.g., if the broker is down or network drops it). |
| **`acks=1`** | **Leader acknowledges** — producer waits only for the partition **leader** broker to confirm it wrote the message. | Balanced speed, but **if the leader crashes before followers copy the message**, that data is lost. |
| **`acks=all`** | **All required in-sync replicas (ISR) acknowledge** — producer waits until the leader **and** all required follower replicas confirm they have the message. | **Strongest durability** (no data loss even if the leader fails), at the cost of **slightly higher latency**. |

- **Best Practice for Important Events:** Use **`acks=all`** together with **idempotent production** (`enable.idempotence=true`), which ensures that if the producer retries a message after a network hiccup, Kafka won't save duplicate copies of the same event.
