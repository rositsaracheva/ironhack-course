### 1. Full Architecture of Apache Kafka : with your comments/explanation

Apache Kafka is a system that allows applications to exchange data in real time.

For example, when someone buys a product on Amazon, the online shop sends an event to Kafka.

The application sending the event is called a **producer**. Kafka organises the events into categories called **topics**, and each topic can be divided into **partitions** to distribute the workload (and keep events in order within each partition).

Kafka runs on servers called **brokers**. Several brokers working together form a **cluster**, where **KRaft controllers** manage the cluster metadata and partition leadership. Brokers can also replicate data so that the system keeps working if a server fails.

Other applications, called **consumers**, read the events. For example, the warehouse can prepare the package, an email service can notify the customer, and analytics can record the sale. Consumers are organised into **consumer groups**: different groups (like different departments — warehouse, email, analytics) each get all the events independently, while multiple consumers inside the same group (like coworkers in the warehouse) split the partitions so they work faster without duplicating work.

Consumers use **offsets** to track their progress (an offset is a number that identifies the position of an event inside a partition), and Kafka keeps the events for a configured period, which allows them to be read again.

In short, Kafka acts as a central system that connects applications and allows them to share information reliably and quickly. It is a push and pull tecnique.

### 2. Class Notes: Handling Consumer Lag & Out-of-Order Events Across Partitions

#### What Is Consumer Lag?

- **Consumer Lag** is how far behind a consumer is compared to the latest message in its partition (`Lag = Latest Offset − Consumer Offset`).
- In a consumer group, different consumers (`X`, `Y`, `Z`) read different partitions independently and at different speeds, so one consumer can lag behind another.

#### Class Example (Why Lag Can Cause Wrong Data)

Suppose the same user updates their email twice:

- **Event `101` (2:00 PM):** `blessing123@gmail.com` → Producer `P` sends it to **Partition 0** (read by **Consumer `X`**)
- **Event `104` (2:04 PM):** `blessing789@gmail.com` → Producer `P` sends it to **Partition 1** (read by **Consumer `Y`**)

If **Consumer `X` is lagging** (slower) while **Consumer `Y` is fast**:

1. **Consumer `Y`** reads Event `104` (`blessing789@gmail.com`, 2:04 PM) **first** and writes it to the database (via **Kafka Connect / KC**).
2. Later, **Consumer `X`** catches up and reads the older Event `101` (`blessing123@gmail.com`, 2:00 PM) **second**, writing it to the database.
3. **Problem:** The older 2:00 PM email overwrites the newer 2:04 PM email! This happens because Kafka **only guarantees order within a single partition**, not across different partitions.

#### How to Handle & Prevent This

1. **Use a Message Key (Same Entity → Same Partition):**
   - Attach a key like `user_id` when producing the event. Kafka sends all messages with the **same key to the same partition** (so both `101` and `104` go to Partition 0). Because only one consumer (`X`) reads Partition 0 in offset order, `101` (2:00 PM) is always processed before `104` (2:04 PM) — even if Consumer `X` lags.
2. **Timestamp / Version Check at the Database (Sink):**
   - Store the event timestamp with the record and only update if `incoming_timestamp > existing_timestamp`, so a late 2:00 PM event can never overwrite a newer 2:04 PM event.
3. **Monitor & Reduce Consumer Lag:**
   - Track consumer lag per partition, optimize slow consumers, and scale consumers (up to the number of partitions) to keep lag low.

### 3. Class Notes: Producer Acknowledgements (`acks`: `0`, `1`, and `all`)

When a producer sends a message to Kafka, the `acks` setting controls **how many broker confirmations** the producer waits for before considering the write successful (speed vs. safety trade-off):

| Setting                | Meaning                                                                                                                                                                  | Trade-off                                                                                                                 |
| :--------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------ |
| **`acks=0`**   | **No wait** — producer sends the message and does not wait for any confirmation from Kafka.                                                                       | Fastest, but**message loss can go unnoticed** (e.g., if the broker is down or network drops it).                    |
| **`acks=1`**   | **Leader acknowledges** — producer waits only for the partition **leader** broker to confirm it wrote the message.                                          | Balanced speed, but**if the leader crashes before followers copy the message**, that data is lost.                  |
| **`acks=all`** | **All required in-sync replicas (ISR) acknowledge** — producer waits until the leader **and** all required follower replicas confirm they have the message. | **Strongest durability** (no data loss even if the leader fails), at the cost of **slightly higher latency**. |

- **Best Practice for Important Events:** Use **`acks=all`** together with **idempotent production** (`enable.idempotence=true`), which ensures that if the producer retries a message after a network hiccup, Kafka won't save duplicate copies of the same event.

### 4. Class Notes: Serialization and Event Contracts

**Key Idea:** Kafka only stores raw **bytes** — it does not inspect or care what is inside a message. That means the **Producer** (which converts data into bytes = **serialization**) and the **Consumer** (which converts bytes back into data = **deserialization**) must agree on the exact format and structure (**event contract**).

#### Example Event Contract (JSON)

```json
{
  "event_id": "...",
  "schema_version": 1,
  "event_type": "order_paid",
  "event_time": "...",
  "order_id": "ORD-3001",
  "amount": 1799.00
}
```

#### Common Serialization Formats

| Format                               | Contract & Trade-off                                                                                                   |
| :----------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| **JSON**                       | Human-readable and easy to debug, but the schema is separate (takes more space and isn't strictly enforced by itself). |
| **Avro**                       | Compact binary format with**strong schema evolution** (very common in Kafka + Schema Registry).                  |
| **Protobuf**                   | Compact, strongly typed binary format, widely used across microservices.                                               |
| **Delimited text** (e.g., CSV) | Simple, but**easy to misuse** (breaks easily if fields change or contain commas/newlines).                       |

- **Best Practice Before Publishing:** Always validate **required fields**, **data types**, **`event_id`**, **`event_time`**, and **`schema_version`** before sending an event to Kafka so bad data doesn't break downstream consumers.

### 5. Class Notes: Python Producer Pattern & What Is `localhost:9092`?

#### The 5 Production Best Practices for a Python Producer

1. **Business key** (`key=order_id`) — keeps all events for the same entity (e.g., same order) in the same partition and in order.
2. **`acks="all"`** — waits for the leader and all in-sync replicas to confirm the write (strongest durability).
3. **Idempotence on** (`"enable.idempotence": True`) — prevents duplicate messages if the producer retries after a network hiccup.
4. **Delivery callback** (`callback=delivered`) — reports whether each message succeeded or failed.
5. **`flush()` before exit** — ensures all queued messages are actually sent before the script stops.

#### Example Code (with Line-by-Line Notes)

```python

    print(err if err else "Delivered")

# I flush the queue before exiting so no messages are left unsent.
```

#### What Is `localhost` (and `localhost:9092`)?

- **`localhost`** (IP address `127.0.0.1`) always means **"this exact computer I am working on right now"** (my own Mac/Windows, not a remote server on the internet).
- **`:9092`** is the **port number** — think of `localhost` as the building address (my computer) and `9092` as the apartment/door number where Kafka is listening. When we started Docker with `-p 9092:9092`, we connected port `9092` on my Mac to Kafka inside the container.
- So `"bootstrap.servers": "localhost:9092"` simply tells Python: *"Connect to the Kafka broker running locally on my computer at port 9092."* (In a real company/production environment, you would replace `localhost:9092` with the real server addresses of the Kafka cluster brokers.)

#### What Is `flush()`?
- When I call `producer.produce(...)`, Kafka does not send each message one by one — it puts them in a local memory buffer (like an **outbox tray**) to send them fast in batches in the background.
- **`producer.flush()`** tells Python: **"Wait here until the outbox tray is completely empty and every queued message has been delivered to Kafka."** Without `flush()`, the script could exit while the last messages are still sitting in memory, losing them.

### 6. Class Notes: Kafka Message Keys & Partition Routing

#### What Is a Key?
- A **key** is an identifier attached to a Kafka event — usually a unique business ID such as `customer_id` (`c101`, `c102`, `c103`), `order_id`, or a file name (like `sample.txt` in Lab 2).

#### How Kafka Uses Keys Internally (Class Example: `orders` Topic)
When a producer sends an event **with a key**, Kafka internally runs a hash function on the key (`hash(key) % num_partitions`) to decide which partition it goes to. Because the same key always hashes to the same partition, all events for the same entity stay together:

| Key (`orders`) | Assigned Partition |
| :--- | :--- |
| **`c101`** | **Partition `0`** |
| `c102` | Partition `1` |
| `c103` | Partition `2` |
| **`c101`** *(second event)* | **Partition `0`** *(always the same partition!)* |

#### Why Use a Key? (Avoiding Out-of-Order Data)
- Kafka only guarantees **sequential ordering within a single partition**.
- By giving every event for `c101` the same key (`c101`), Kafka guarantees all of `c101`'s events go into **Partition 0** and are read in exact sequential order — avoiding the situation where events arrive out of order.

#### What If You Do NOT Send a Key (`key=None`)?
- If no key is provided, Kafka distributes messages across partitions automatically (e.g., round-robin / sticky partitioning) to spread the workload evenly.
- While that balances load across brokers, related events for the same customer or order can land in **different partitions**, meaning **sequential order is NOT guaranteed**.

### 7. Kafka Glossary 

| Term | Explanation |
| :--- | :--- |
| **Kafka** | A distributed platform that lets applications send, store, and read data (events) in real time, reliably and at high speed. |
| **Broker daemons** | The background server processes running Kafka; each broker stores partitions and handles requests from producers and consumers. |
| **Producer** | An application that creates and sends (publishes) events into a Kafka topic. |
| **Consumer** | An application that reads (subscribes to) events from a Kafka topic. |
| **Consumer groups** | Teams of consumers: **different groups** (like warehouse, email, analytics) each get all events independently, while consumers **inside the same group** split the partitions to share the work without duplicating it. |
| **acks** | Producer acknowledgement setting controlling how many broker confirmations to wait for (`0` = no wait, `1` = leader only, `all` = leader + all in-sync replicas for maximum safety). |
| **Idempotency** | A producer setting (`enable.idempotence=True`) that ensures even if a message is retried after a network glitch, Kafka stores it only once (no duplicates). |
| **Partition** | A slice (sub-log) of a topic that allows parallelism and scaling; message order is guaranteed **within** a single partition. |
| **Replication factor** | How many copies of each partition exist across different brokers (e.g., replication factor `3` = 1 leader + 2 followers) so data isn't lost if a broker fails. |
| **Keys (hash keys)** | An ID attached to an event (like `customer_id` or `order_id`); Kafka hashes the key so all events with the **same key always go to the same partition** and stay in exact order. |
| **Topic** | A named category or stream where related events are stored (like `orders` or `file-topic`). |
| **Event** | A single record/message describing something that happened at a point in time (e.g., a customer placing an order). |
| **Offset** | A sequential number (`0, 1, 2, ...`) that marks the exact position of an event inside a partition so consumers know where they left off. |
| **KRaft** | Kafka's built-in control plane (replacing ZooKeeper) that manages cluster metadata, broker membership, and partition leadership. |
| **bootstrap-server** | The initial broker address (like `localhost:9092`) that a producer or consumer connects to first so it can discover the rest of the Kafka cluster. |
| **`flush()`** | Tells the producer to wait until all buffered/queued messages in memory are actually delivered to Kafka before the program exits. |
| **`retries*`** | Tells the producer to automatically resend a message if a temporary error happens (e.g., brief network hiccup or leader switch) — best paired with **idempotency** to avoid duplicates. |
| **Confluent Kafka vs Apache Kafka** | **Apache Kafka** is the free, open-source core engine; **Confluent** is a commercial platform built on top of Apache Kafka that adds enterprise tools (Schema Registry, managed cloud, extra connectors, and the `confluent-kafka` Python client). |
