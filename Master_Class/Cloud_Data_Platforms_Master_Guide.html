1. The Big Picture: Why Do All These Tools Exist?

If your head is spinning with names like Spark, Databricks, Parquet, Avro, Delta Lake, and Snowflake, start right here. Every single tool fits into one of 4 simple jobs.

🏠 The Restaurant Analogy (Understand Everything in 60 Seconds)

Imagine running a giant restaurant that serves millions of meals (queries & reports):

  • Cloud Storage (AWS S3 / Azure Blob / Google Cloud Storage): The Giant Warehouse Fridge where all ingredients (raw data files) are stored cheaply.
  • File Formats (CSV, JSON, Parquet, Avro, Delta Lake): The Tupperware Containers inside the fridge. A CSV is a messy plastic bag; Parquet is a neatly labeled vacuum-sealed container; Delta Lake is a smart container with a barcode log tracking every change.
  • Compute Engine (Apache Spark / Snowflake Virtual Warehouse): The Kitchen & Chefs. Storage just sits there doing nothing! To cook (filter, join, aggregate, or train AI), you need chefs (Nodes / Clusters / Virtual Warehouses) with CPU and RAM.
  • The Platform (Databricks vs. Snowflake): The Complete Restaurant Management System that gives you the workspace, security guards, notebooks/worksheets, and automatic chef scheduling in one browser tab.

1️⃣ Data Lake Storage First

What it is: A massive folder in the cloud (like AWS S3) storing raw files of any type: CSVs, Parquet, Avro, JSON, PDFs, audio, images.

  • Pros: Extremely cheap; holds any data type (structured, semi-structured, unstructured); great for Data Science & ML.
  • Cons: Can turn into a "Data Swamp" — no ACID transactions, no UPDATE/DELETE, no Time Travel on plain files.

2️⃣ Data Warehouse Snowflake

What it is: A centralized SQL database built specifically for fast Business Intelligence (BI), analytics, and reporting (OLAP).

  • Pros: Super clean, fast SQL, ACID transactions, Time Travel, role-based security, zero maintenance.
  • Cons: Built primarily for structured & semi-structured tables (SQL analytics), not raw unstructured files like video/audio.

3️⃣ Data Lakehouse Databricks

What it is: Combines the cheap, flexible file storage of a Data Lake with the reliability and SQL features of a Data Warehouse.

  • How it works: Uses Delta Lake on top of Parquet files so you get ACID transactions, UPDATE/DELETE, and Time Travel directly on your Data Lake!
  • Best for: Big Data ETL in PySpark, Machine Learning / AI, AND SQL analytics in one place.
💡 Key Concept — OLTP vs. OLAP (Very Common in Interviews!):
• OLTP (Online Transaction Processing): Databases that run the live app/website (e.g., PostgreSQL, MySQL). Fast at inserting/updating 1 single order at a time (Row-oriented).
• OLAP (Online Analytical Processing): Data Warehouses & Lakehouses (e.g., Snowflake, Databricks). Built for scanning millions of historical rows to calculate total revenue or trends (Column-oriented).

2. Essential Vocabulary Dictionary (Clusters, Nodes, Volumes, Stages...)

Type any word below (e.g., cluster, node, volume, stage, warehouse, partition) or filter by category.

Node Compute

Plain English: A single computer (virtual server) in the cloud with its own CPU (processor) and RAM (memory).

When data is huge, 1 computer is too slow. So cloud platforms rent multiple computers (nodes) and connect them together.

Analogy: 1 Node = 1 Chef working in the kitchen.

Cluster Compute

Plain English: A team of Nodes (computers) connected together that work in parallel as if they were one giant supercomputer.

  • In Databricks / Spark, a Cluster has 1 Driver Node (the boss) + multiple Worker Nodes (the helpers).
  • When your code finishes, the cluster turns off so you stop paying for the computers!
Analogy: 1 Cluster = A full Kitchen Team (1 Head Chef + 8 Line Cooks).

Driver Node vs. Worker Node Databricks / Spark

Inside a Spark / Databricks Cluster, nodes have two roles:

  • Driver Node (1 per cluster): The "Brain / Boss". It reads your Python/SQL notebook, breaks the job into small tasks, and assigns them to Worker Nodes.
  • Worker Nodes (1 to 100s): The "Muscle". Each Worker Node holds Executors that actually read the data slices (partitions), filter/join them in parallel, and send the result back.

Virtual Warehouse Snowflake Compute

Plain English: Snowflake's name for a Compute Cluster! Despite the word "Warehouse", a Virtual Warehouse stores ZERO permanent data — it is 100% CPU + RAM used to run SQL queries and load data.

  • Sized like T-shirts: X-Small (1 node/credit), Small (2), Medium (4), up to 6X-Large. Each step up doubles compute power & cost.
  • AUTO_SUSPEND = 60 turns it off after 60 seconds of inactivity to save money.
  • AUTO_RESUME = TRUE wakes it up in 1 second as soon as you press Play on a query.

Volume (Unity Catalog Volume) Databricks Storage

Plain English: A governed folder for raw files inside Databricks Unity Catalog.

  • Tables only hold structured rows & columns. Where do you put raw .csv, .parquet, .avro, .json, or .pdf files before turning them into tables? Inside a Volume!
  • Path format: /Volumes/<catalog>/<schema>/<volume_name>/file.csv
  • Replaces the old legacy DBFS (dbfs:/FileStore/...) in modern Databricks.
Analogy: A Volume in Databricks is the exact equivalent of an Internal Stage in Snowflake!

Stage (`@stage_name`) Snowflake Storage

Plain English: The "Loading Dock / Waiting Room" folder where raw files (like uk_travel_bookings.csv) sit before you load them into a Snowflake table with COPY INTO.

  • Internal Stage: Folder inside Snowflake itself (Named Stage @my_stage, User Stage @~, or Table Stage @%my_table).
  • External Stage: Points to your company's own cloud bucket (s3://my-bucket/, Azure, or GCP) using a secure Storage Integration (no hardcoded passwords!).

Unity Catalog Databricks Governance

Plain English: The central security, governance, and organization system in Databricks that organizes all data in a 3-level hierarchy:

Catalog.Schema.Table_or_Volume (e.g., workspace.default.netflix_titles)

  • Controls who can read/write which tables, volumes, and AI models across all workspaces.

Micro-partitions & Clustering Keys Snowflake Storage

Plain English: Whenever you load data into a Snowflake table, Snowflake automatically chops it into tiny, immutable, compressed columnar files called Micro-partitions (50–500 MB uncompressed).

  • Snowflake stores the MIN and MAX values of every column in each micro-partition.
  • Query Pruning: If you search WHERE booking_date = '2026-08-20', Snowflake skips 99% of micro-partitions without even opening them!
  • Clustering Key: For huge multi-terabyte tables, you can tell Snowflake CLUSTER BY (order_date) to keep micro-partitions sorted.

COPY INTO vs. Snowpipe Snowflake Ingestion

How do files get from a Stage into a Table?

  • COPY INTO (Bulk Batch): You run it manually or on a schedule. Uses your Virtual Warehouse. Great for loading large historical batches or transforming columns during load.
  • Snowpipe (Continuous Serverless): Event-driven (`AUTO_INGEST = TRUE`). As soon as a new file lands in AWS S3, S3 sends an notification (SQS) and Snowpipe loads it automatically within minutes using serverless compute!

Streams & Tasks Snowflake Pipelines

How Snowflake automates continuous data pipelines:

  • Table Stream (CDC - Change Data Capture): Like a bookmark/security camera on a table that records only newly inserted, updated, or deleted rows since the last time you checked.
  • Task: A built-in scheduler (cron job) inside Snowflake that runs a SQL statement or Stored Procedure automatically (e.g., every hour) to process new rows from a Stream.

Lazy Evaluation (Transformations vs. Actions) PySpark

In PySpark, when you write df.filter(...) or df.select(...), Spark does not execute anything yet!

  • Transformations (Lazy): select(), filter(), withColumn(), groupBy(), join(). They only build an execution plan (recipe).
  • Actions (Eager): show(), display(), count(), collect(), write. They trigger the cluster to actually process the data!

Scaling Up vs. Scaling Out High-Frequency Interview Term

Two ways to add compute power in Snowflake:

  • Scale Up (Vertical — Resize Warehouse): Change X-Small $\rightarrow$ Large (bigger engine). Best when 1 complex, heavy query is running slowly.
  • Scale Out (Horizontal — Multi-Cluster Warehouse): Add more clusters (`MIN_CLUSTER_COUNT = 1, MAX_CLUSTER_COUNT = 4`). Best when 100 analysts run queries at the exact same time (prevents queuing!).

3. File Formats Compared: CSV vs. JSON vs. Avro vs. Parquet vs. Delta Lake

Why did we spend a whole day learning Parquet and Avro instead of just using CSVs? Because how data is organized on disk changes speed and cost by 10x!

Row-Based Storage (CSV, Avro)

Stores data row by row on disk:

[2001, Oliver, Spain, £320] [2002, Amelia, Portugal, £450]
  • Fast at WRITING new full records (e.g., logging a new tweet or order event).
  • Slow at ANALYTICS: If you only want SUM(price), the computer still has to read every single column (name, city, country) of every row!

Columnar Storage (Parquet, ORC, Delta, Snowflake)

Stores data column by column on disk:

IDs: [2001, 2002] | Countries: [Spain, Portugal] | Prices: [£320, £450]
  • Fast at READING / ANALYTICS (OLAP): If you query SUM(price), it reads only the Prices block and skips all other columns!
  • Huge Compression (3–5x smaller): Since all values in a column have the same data type (e.g., `"Spain", "Spain", "Spain"`), compression (Snappy, ZSTD) shrinks files dramatically.
Format Orientation Human Readable? Stores Data Types (Schema)? Best Use Case
CSV / TSV Row-based ✅ Yes (Plain text) ❌ No (Everything is text unless parsed) Small datasets, Excel exports, quick manual inspection.
JSON Semi-structured ✅ Yes (Text) ⚠️ Basic JSON types Web APIs, nested events, clickstreams (loaded into Snowflake VARIANT).
Apache Avro (.avro) Row-based (Binary) ❌ No (Binary + JSON header) ✅ Yes (Embedded JSON schema header) Streaming & Kafka, write-heavy pipelines, and strong Schema Evolution (like your Twitter Avro lab!).
Apache Parquet (.parquet) Columnar (Binary) ❌ No (Binary + footer metadata) ✅ Yes (Stored in file footer with min/max stats) Big Data Analytics (Spark, Snowflake staging). 3–5x faster & smaller than CSV. Read-only (immutable).
Delta Lake (delta) Columnar (Parquet + _delta_log) ❌ No (Parquet + JSON log) ✅ Yes + Enforced automatically Databricks default format. Adds ACID transactions, UPDATE/DELETE/MERGE, and Time Travel to Parquet!

4. Databricks, PySpark & Delta Lake

How all the pieces inside your Databricks workspace fit together.

📂 How Databricks Organizes Data (Unity Catalog)

Whenever you look at the Catalog Explorer in Databricks, it follows a strict 3-level hierarchy:

📦 Catalog (e.g., workspace or main)
  └── 📁 Schema / Database (e.g., default or sales)
        ├── 📊 Tables (Delta tables queried with SQL / PySpark)
        ├── 👁️ Views (Saved SQL queries)
        └── 🗂️ Volumes (Folders holding raw files: CSV, Parquet, Avro, PDF)

🔺 Delta Lake & The Medallion Architecture

In Databricks projects (and interviews!), data flows through 3 layers of Delta tables called the Medallion Architecture:

  • 🥉 Bronze Layer (Raw): Raw data ingested straight from Volumes/S3 (exact copy of source CSV/JSON/Avro, nothing lost).
  • 🥈 Silver Layer (Cleaned & Filtered): Nulls handled, duplicates removed, data types fixed, tables joined.
  • 🥇 Gold Layer (Business-Ready Aggregations): Final KPIs, revenue per month, customer rankings ready for dashboards & BI!

⏱️ Databricks Essential Commands (PySpark & Delta Time Travel)

Reading & Writing Files in PySpark:

# Read CSV from a Unity Catalog Volume
df = spark.read.option("header", True).option("inferSchema", True) \
    .csv("/Volumes/workspace/default/my_volume/customers.csv")

# Write as Parquet or Delta
df.write.mode("overwrite").parquet("/Volumes/.../output_parquet")
df.write.mode("overwrite").saveAsTable("workspace.default.customers")

Delta Lake Time Travel in SQL:

-- 1. Check version history (0, 1, 2...)
DESCRIBE HISTORY customers;

-- 2. Query an older version
SELECT * FROM customers VERSION AS OF 0;

-- 3. Roll back the table to an older version
RESTORE TABLE customers TO VERSION AS OF 0;

5. Snowflake Deep Dive (Everything from Day 1 & Day 2 Slides)

Snowflake is a 100% Cloud-Native Data Warehouse delivered as SaaS (Software-as-a-Service) that runs on AWS, Azure, or GCP. Its #1 innovation is separating Storage, Compute, and Cloud Services into 3 independent layers.

🧠 Layer 1: Cloud Services Layer ("The Brain")

Handles Authentication & Access Control (RBAC), Query Parsing & Optimization, Metadata Management (micro-partition min/max stats, Time Travel pointers), and ACID Transaction Coordination. Fully managed by Snowflake.

⬇️ Dispatches optimized execution plan ⬇️

⚡ Layer 2: Query Processing Layer (Compute — Virtual Warehouses)

Independent MPP (Massively Parallel Processing) compute clusters made of cloud nodes (CPU + RAM + local SSD cache). You can run multiple Virtual Warehouses at the same time (e.g., ETL_WH for loading data and BI_WH for analysts) on the exact same data without slowing each other down! Billed per second when running.

⬇️ Reads & writes compressed columnar data ⬇️

💾 Layer 3: Database Storage Layer (Centralized Cloud Storage)

Stores all data in cloud object storage (AWS S3 / Azure Blob / GCS), automatically converted into compressed, encrypted, columnar Micro-partitions (50–500 MB). Billed separately per Terabyte/month.

💡 Why is Snowflake called a "Hybrid" Architecture? (Day 1 Slide 19–21):
• It combines Shared-Disk (one central cloud storage layer accessible to all compute clusters) with Shared-Nothing (each Virtual Warehouse is an independent MPP cluster where nodes process data in parallel with their own local CPU/RAM/cache).

📋 3 Table Types in Snowflake

  • Permanent Table (Default): Persists until dropped. Has Time Travel (1 to 90 days) + 7-day Fail-safe. Best for production business data.
  • Transient Table: Persists until dropped, NO Fail-safe (0–1 day Time Travel). 30–50% lower storage overhead. Best for staging / intermediate ETL tables (CREATE TRANSIENT TABLE...).
  • Temporary Table: Exists only during your current session; disappears automatically when you close the session (CREATE TEMPORARY TABLE...).

👁️ 3 View Types in Snowflake

  • Standard View: A saved SQL query executed on-demand. Uses 0 storage. Simplifies complex joins or hides columns.
  • Materialized View: Pre-computes and physically stores the query result, automatically refreshing when the base table changes. Consumes storage, but makes heavy BI dashboard aggregations super fast!
  • Secure View: Hides the underlying SQL definition and prevents query-optimizer data leaks. Used for Secure Data Sharing & privacy.

🛡️ Time Travel, Fail-safe & Cloning

  • Time Travel: Query or restore past data via SQL using AT(OFFSET => ...), BEFORE(STATEMENT => ...), or UNDROP TABLE (1 day Standard, up to 90 days Enterprise).
  • Fail-safe: 7-day period after Time Travel ends. Users cannot query it — only Snowflake Support can recover it in emergencies.
  • Zero-Copy Cloning: CREATE TABLE dev_t CLONE prod_t; Instant copy with $0 extra storage because it only copies metadata pointers to the original micro-partitions!

📦 4 Types of Snowflake Stages

  • 1. User Stage (@~): Automatic private folder for your user.
  • 2. Table Stage (@%table_name): Automatic folder attached to a single table.
  • 3. Named Internal Stage (@my_stage): Shared folder inside Snowflake (what we used in class!).
  • 4. External Stage: Points to AWS S3 / Azure / GCS using a STORAGE INTEGRATION (best for enterprise production).

Golden Rule for Loading: Aim for compressed files (Parquet or ZSTD/GZIP CSV) sized 100–250 MB so Virtual Warehouse nodes load them in parallel!

🔐 Role-Based Access Control (RBAC)

Snowflake never grants permissions directly to users — permissions are granted to Roles, and Roles are granted to Users:

  • ACCOUNTADMIN: Top-level boss (billing, security, everything). Never use for daily analyst work!
  • SECURITYADMIN: Creates users, roles, and grants privileges.
  • SYSADMIN: Creates and manages databases, schemas, and warehouses.
  • PUBLIC: Automatically granted to every user.

🧩 Semi-Structured Data (`VARIANT`)

Snowflake stores JSON, Avro, ORC, Parquet, and XML directly inside a VARIANT column (up to 16 MB per row) without needing upfront schemas:

SELECT
  event:booking_id::INT,
  f.value:name::STRING
FROM booking_events,
LATERAL FLATTEN(input => event:extras) f;

7. Top 20 Job Interview Questions & Model Answers

Click on any question below to reveal the clear, structured answer you can give in a Data Analyst / Data Engineer interview.

1. What is the difference between a Data Lake, a Data Warehouse, and a Data Lakehouse?
  • Data Lake: Stores raw data in any format (CSV, Parquet, JSON, images) on cheap cloud object storage (like S3). Flexible, but lacks ACID transactions and SQL governance on its own.
  • Data Warehouse (e.g., Snowflake): Stores structured and semi-structured data optimized for fast SQL analytics and BI reporting, with full ACID transactions and governance.
  • Data Lakehouse (e.g., Databricks with Delta Lake): Combines both by adding a transactional metadata layer (Delta Lake) directly on top of open Parquet files in a Data Lake, supporting both BI SQL analytics and Machine Learning in one platform.
2. Explain Snowflake's 3-Layer Architecture and why separating Storage and Compute matters.

Snowflake separates its architecture into three independent layers:

  1. Database Storage Layer: Stores data in compressed, columnar micro-partitions in cloud object storage.
  2. Query Processing Layer (Compute): Independent Virtual Warehouses (MPP clusters) that execute queries.
  3. Cloud Services Layer: The "brain" handling authentication, metadata, query optimization, and ACID transactions.

Why it matters: In traditional databases, storage and compute are tied together. In Snowflake, they scale independently — you can store petabytes cheaply with compute turned off (AUTO_SUSPEND), or spin up multiple Virtual Warehouses for different teams (ETL vs. BI) querying the same data simultaneously with zero resource contention.

3. What is a Cluster and a Node in Databricks / Apache Spark?

A Node is a single virtual machine (server with CPU and RAM). A Cluster is a group of nodes working together in parallel:

  • Driver Node (1 per cluster): Coordinates the job, parses your PySpark/SQL code, creates the execution plan, and distributes tasks.
  • Worker Nodes (Many): Execute the actual tasks in parallel on partitions of data using Executors and return results.
4. Why is Parquet preferred over CSV for Big Data analytics?
  1. Columnar Format: Parquet stores data by column rather than by row. Analytical queries that only select 3 out of 50 columns only read those 3 columns from disk (Column Pruning).
  2. Higher Compression: Because similar data types sit together in each column, Parquet compresses 3–5x smaller than CSV.
  3. Embedded Schema & Statistics: Parquet stores column data types and min/max statistics in its footer, allowing engines like Spark and Snowflake to skip irrelevant row groups (Predicate Pushdown).
5. When would you choose Avro over Parquet?

Avro is a row-based binary format, whereas Parquet is column-based.

  • Choose Avro for write-heavy workloads, Kafka event streaming, and landing raw records where entire rows are written at once and schemas evolve frequently.
  • Choose Parquet (or Delta Lake) for read-heavy analytical queries (OLAP) where you aggregate and filter specific columns across millions of rows.
6. What is Delta Lake and how does it improve upon plain Parquet?

Delta Lake is an open-source storage format used by default in Databricks. Under the hood, it consists of Parquet data files + a JSON transaction log folder (_delta_log).

Plain Parquet files are immutable and lack transactions. Delta Lake adds:

  • ACID Transactions (atomic, crash-safe writes).
  • DML Support: Ability to run UPDATE, DELETE, and MERGE (upserts).
  • Time Travel: Query or restore any previous version (VERSION AS OF).
  • Schema Enforcement & Evolution: Prevents bad data types from corrupting tables.
7. What is the difference between a Unity Catalog Volume (Databricks) and a Stage (Snowflake)?

They solve the exact same problem on their respective platforms: providing a governed location to store raw files (CSV, Parquet, Avro, JSON) before loading them into tables.

  • In Databricks, a Volume is a Unity Catalog object accessed like a folder path (/Volumes/catalog/schema/volume/file.csv).
  • In Snowflake, a Stage (Internal @stage or External pointing to S3) holds files that you load into tables via COPY INTO or Snowpipe.
8. In Snowflake, what is the difference between Scaling Up and Scaling Out a Virtual Warehouse?
  • Scaling Up (Resizing, e.g., X-Small to Large): Doubles the compute nodes inside a single cluster. Use this to speed up slow, complex, heavy queries or large data loads.
  • Scaling Out (Multi-Cluster Warehouse, e.g., Min 1 to Max 4 clusters): Automatically spins up additional clusters of the same size when queries start queuing. Use this for high concurrency (e.g., 200 business users opening dashboards at 9:00 AM).
9. What is the difference between Permanent, Transient, and Temporary tables in Snowflake?
  • Permanent (Default): Persists until dropped; supports Time Travel (up to 90 days on Enterprise) + 7-day Fail-safe. Used for production tables.
  • Transient: Persists until dropped; has 0–1 day Time Travel and no Fail-safe, reducing storage costs. Ideal for staging/ETL tables.
  • Temporary: Exists only within the current user session and is automatically dropped when the session ends. Ideal for scratch work.
10. What is the difference between Time Travel and Fail-safe in Snowflake?
  • Time Travel (1 to 90 days): Self-service feature allowing users to query historical data (AT / BEFORE), clone past snapshots, and UNDROP tables directly via SQL.
  • Fail-safe (7 days): Begins immediately after the Time Travel retention period ends. It is a non-configurable disaster recovery period accessible only by contacting Snowflake Support (not queryable by users).
11. How does Zero-Copy Cloning work in Snowflake, and why is it almost free at creation?

When you run CREATE TABLE orders_dev CLONE orders;, Snowflake does not duplicate the physical micro-partitions. Instead, it creates new metadata pointers in the Cloud Services layer pointing to the exact same underlying micro-partitions.

Because no data is copied, it finishes in seconds and costs $0 in extra storage at creation time. You only pay for additional storage if you modify (`INSERT`/`UPDATE`/`DELETE`) rows in the clone, which creates new micro-partitions for just those changes.

12. When should you use `COPY INTO` vs. `Snowpipe` in Snowflake?
  • Use COPY INTO (Batch): When loading large volumes of files on a scheduled batch (hourly/daily), when you want explicit control over the Virtual Warehouse size, or when performing complex transformations during load.
  • Use Snowpipe (Continuous Serverless): When small files arrive continuously in cloud storage (like S3) and you want event-driven, near real-time ingestion (within minutes) using serverless compute without managing a running warehouse.
13. What is the ideal file size and format when staging files for Snowflake?

Snowflake recommends staging compressed files between 100 MB and 250 MB (or using Parquet with ZSTD compression).

Why? If you upload one single 50 GB file, only 1 compute thread can read it while the rest of the Virtual Warehouse sits idle. Splitting data into 100–250 MB files allows all compute nodes in the Virtual Warehouse to load files in parallel.

14. What is the difference between a Standard View, a Materialized View, and a Secure View?
  • Standard View: Saves the SQL query text only; re-runs the query against the base table every time. Zero storage cost.
  • Materialized View: Pre-computes and physically stores the result set, automatically refreshing in the background when the base table changes. Costs storage/compute, but makes repetitive aggregations much faster.
  • Secure View: Hides the view's SQL definition from unauthorized users and prevents query optimizer workarounds that could expose filtered rows. Essential for external Data Sharing.
15. How do you handle JSON / Semi-structured data in Snowflake?

Load the JSON into a column of type VARIANT (using PARSE_JSON or a JSON file format). Snowflake automatically extracts columnar metadata for fast querying. You can query nested fields using colon/dot notation (event:customer.name::STRING) and unnest arrays into rows using LATERAL FLATTEN(input => event:items).

16. What is the `QUALIFY` clause in Snowflake and Databricks SQL?

Just like WHERE filters raw rows and HAVING filters GROUP BY aggregations, QUALIFY filters the results of Window Functions (like ROW_NUMBER(), RANK(), or LAG()) directly without needing a subquery or CTE!

SELECT package_type, destination_city, SUM(travellers * price_per_person_gbp) AS rev
FROM bookings
GROUP BY package_type, destination_city
QUALIFY ROW_NUMBER() OVER (PARTITION BY package_type ORDER BY rev DESC) <= 2;
17. What are Micro-partitions and Query Pruning in Snowflake?

Snowflake automatically stores all table data in immutable 50–500 MB columnar units called Micro-partitions, recording metadata (such as min/max range, null count, and distinct values) for every column in the Cloud Services layer.

When a query has a WHERE filter, Query Pruning checks that metadata first and skips reading any micro-partition whose min/max range doesn't match the filter, scanning only a tiny fraction of the table.

18. What are Streams and Tasks in Snowflake?
  • Streams: Implement Change Data Capture (CDC) by tracking inserts, updates, and deletes on a table so you can process only new/changed rows.
  • Tasks: Schedule SQL statements or Stored Procedures to run on a timer (cron schedule) or when a Stream has new data, forming an automated end-to-end ELT pipeline.
19. Why does `AUTO_SUSPEND` matter so much in Snowflake and Databricks?

Compute clusters (Snowflake Virtual Warehouses and Databricks Clusters) are billed for the time they are running, even if no queries are executing. Setting AUTO_SUSPEND = 60 (1 minute in Snowflake) or auto-termination in Databricks ensures idle clusters shut down automatically so you never pay for unused compute.

20. How do Role-Based Access Control (RBAC) and Dynamic Data Masking help with GDPR?
  • RBAC: Enforces least-privilege access by granting database/schema/table permissions to functional roles (e.g., ANALYST, MARKETING) rather than giving everyone ACCOUNTADMIN.
  • Dynamic Data Masking: Attaches a masking policy to sensitive PII columns (like customer name or email) so non-privileged roles automatically see *** MASKED *** while authorized roles see the real value — without duplicating the table.
