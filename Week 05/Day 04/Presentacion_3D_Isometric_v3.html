1. The Business Problem

Why Not Just Use CSV for Everything?

CSV is great for humans and Excel, but terrible for distributed engines like Spark, Hive & Impala.

⚠️ 3 Fatal Flaws in Big Data
  • 1. No Embedded Schema (Untyped Text):
    Every value is plain text. Spark or Hive must parse and convert strings into numbers or dates on every read.
  • 2. Huge File Size & Slow Parsing:
    Plain text wastes disk space and CPU cycles splitting commas.
  • 3. Forced Full-Table Scans (100% I/O):
    Because CSV stores data row-by-row, summing just 1 column out of 50 forces the engine to scan the entire file!
✓ Pros: Human-readable & universal for small Landing Zone files.
FULL TABLE SCAN BOTTLENECK QUERY: SELECT SUM(SPENT)
2. Core Storage Architecture

Row-Oriented vs. Column-Oriented Layout

How physical disk organization changes everything for SELECT SUM(Spent)

📦 Row-Oriented (CSV & Avro) WRITE-OPTIMIZED
DISK LAYOUT: ROW BY ROW SCANS ALL BLOCKS
  • Stores whole customer rows together sequentially.
  • Fastest for Writes: Appending a new transaction is instant.
📊 Column-Oriented (Parquet & ORC) READ-OPTIMIZED
DISK LAYOUT: GROUPED BY COLUMN COLUMN PRUNING
  • Groups identical columns together continuously on disk.
  • Fastest for Analytics: Skips unused columns & compresses 85%.
3. Deep Dive: Ingestion & Streaming

Apache Avro: Binary Rows + JSON Schema

The #1 choice for Kafka event streaming and Sqoop Raw Data Lake ingestion.

⚡ Why Data Engineers Love Avro
  • 1. Self-Describing JSON Header (.avsc):
    Every Avro file embeds its own JSON schema in the file header—data types are never lost.
  • 2. Champion of Schema Evolution:
    If MySQL adds a new column next month, Avro reads both old files (v1) and new files (v2) seamlessly without breaking pipelines!
  • 3. Splittable Binary Blocks:
    Sync markers let Spark & MapReduce split large Avro files across parallel executors.
Use Cases: Kafka Streaming • Sqoop (--as-avrodatafile)

4. Deep Dive: Analytical Engine

Apache Parquet: Built for Spark, Impala & Hive

Two analytical superpowers that slash cloud query bills by up to 90%.

🚀 2 Superpowers of Parquet
  • 1. Column Pruning (Skip Columns):
    Only reads the exact columns requested in your SELECT statement.
  • 2. Predicate Pushdown (Skip Row Groups):
    Parquet stores min/max statistics in the footer of every block. If you filter WHERE year = 2026, Parquet skips entire blocks that only contain 2020–2024!
  • 3. Homogeneous Compression (85% Smaller):
    Storing identical data types together lets Snappy & Dictionary Encoding shrink 100 GB down to 15 GB.
Cloud Savings: Less GB scanned = 90% cheaper BigQuery / Athena bills!

6. Conclusion & Production Pipeline

How All Three Work Together in a Modern Data Lake

In production, we don't pick just one—we assign each format to its ideal Data Lake zone!

ZONE 01 // LANDING

📄 CSV / JSON

External vendors, stores, and APIs drop raw files exactly as delivered for initial arrival and audit.

➔ Ingested via Sqoop / Kafka
ZONE 02 // RAW (BRONZE)

⚡ Apache Avro

Writes full rows rapidly with embedded JSON schemas and protects pipelines with Schema Evolution.

➔ Transformed via Spark / Hive
ZONE 03 // CURATED (GOLD)

🚀 Apache Parquet

Spark, Impala & BI Dashboards query clean columnar tables with Column Pruning & Predicate Pushdown!

✓ Ready for Analytics & ML
